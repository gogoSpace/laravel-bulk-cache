# Upgrading and rolling back

This package is still beta. Pin the package version and retain the previous Composer lock file and application release. Test your actual writers, cache stores and loader registrations in an isolated application before deployment. The version-transition check exercises Laravel 12 and 13, portable file and SQLite database stores, and guarded Redis with PhpRedis. It does not establish compatibility with every future release.

The current changes preserve the beta.1 cache envelope (`bc:v1`, envelope version `1`) and refresh job version `1`. Values written by either version remain readable by the other: null, false, zero, empty strings and arrays, nested arrays, and explicit missing values. Key and scope generations remain meaningful in both directions. Rolling code back does not undo an invalidation or restore an older cache generation.

With an unchanged dataset definition, refresh jobs queued by beta.1 can be consumed by the new worker, and jobs queued by the new version can be consumed by beta.1. Disabled new options preserve the previous definition fingerprint; observation settings do not affect it. Enabling required guarantees, adding required dimensions, or changing another definition option can change that fingerprint. A job created for a different definition fails before loading or publishing. Discard or re-dispatch that job using the intended release; repeatedly retrying it cannot repair a definition mismatch.

1. Keep the previous application release and `composer.lock`. Confirm that its loaders and source schema remain usable if you roll back.
2. Stop producing background refresh jobs and let the old refresh queue drain when changing dataset definitions. Stop old workers before replacing their code. Configure a dedicated refresh queue if it must be drained independently of other application jobs.
3. Deploy the pinned package and application changes. Run `php artisan config:clear` and `php artisan config:cache` with the target release's configuration. Restart queue workers from that release. Long-running workers must not keep using the previous code or configuration.
4. Check a cache miss, hit, invalidation, HTTP refresh and queued refresh. Resume background production after these checks pass.
5. For rollback, stop the new workers, restore the previous application release and lock file, rebuild its configuration cache, and start its workers. Apply the same drain/discard rule to changed definitions. Keep the same application namespace only when the application payload meaning and loader contract remain compatible.

For an incompatible future payload or identity change, use a new application-controlled dataset name or prefix. Never switch back to an older populated namespace after writes have continued: those entries may predate the writes. Use a fresh namespace on rollback, or prove every relevant generation was invalidated. Logical invalidation does not physically remove historical values or metadata. Source schema migrations and irreversible database writes require a separate application rollback plan.

Run `composer upgrade:check` from a clean committed checkout. It builds a ZIP for that exact commit, obtains the pinned public beta.1 source commit, and installs each real package version in turn using Composer. Each Laravel consumer retains its SQLite database, cache files, isolated Redis data and serialized queued jobs while the package changes. Separate worker processes execute both directions, with source hashes recorded in the report. Duplicate jobs must refresh once per backend; retained data types and cross-user invalidation must still pass. No package development dependencies or source symlinks are allowed. Missing PHP extensions, Redis, consumers or failed jobs cause a nonzero exit.

The `Tests` workflow requires both the PHP/Testbench matrix and the separate distribution matrix through its `acceptance` job. Configure that job as a required repository check before releasing. The distribution matrix runs clean consumers, installed documentation examples, package checks and version transitions on PHP 8.4 and 8.5; PHP 8.3 is covered with Laravel 12 in the package matrix. A configured workflow is not evidence that a particular commit has passed remote CI.
